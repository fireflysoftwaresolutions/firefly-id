# Native support evidence and privileged administration

The owner authorizes implementation of remaining BPO and privileged-administration controls independent of KYC or third-party services. They selected named administrator accounts with password plus FIDO2/WebAuthn user verification, separate audited emergency access, and consultation/support as the initial BPO scope. The case/authorization owner is not yet defined. These choices authorize preparation and qualification, not changes to real administrator accounts or activation of support verification.

## Boundaries

Jafly remains independent and unchanged. Identity owns credentials and native proof state; it must not invent business cases, employment, mandates, payment permissions or a producer contract. No new public PIN verification endpoint, permissive support owner, customer impersonation or customer token handoff. The external authorization factory remains fail-closed unless exactly one genuine owner implementation is installed and qualified. All repository prose is American English; owner communication is Spanish.

Use the existing isolated checkout. No local Java/Maven, Docker/database/browser or dependency installations; actual native compilation and browser/database qualification run in owned hosted CI. Preserve retained data, failures and source worktrees; never reset counters or create replacement authority to repair uncertainty. No merge, release or CIAM production activation.

## BPO preparation

Complete the native credential-evidence boundary behind the existing authorization SPI. Validate bounded nonempty grant fields, HTTPS issuer boundaries, distinct workforce/customer issuers, narrow PIN-verification action/purpose and a maximum 120-second remaining lifetime. The support producer must independently verify actual current staff, employment/delegation, customer, tenant, genuine case/call and approvals; valid credentials alone cannot supply that decision.

Fence grant replay by a stable issuer/realm-scoped nonce independent of mutable grant fields, in addition to exact full-grant binding. A repeated or altered authorization must not allocate another PIN check. Keep per-PIN-generation counters and reserved slots durable, with three failed checks causing an untimed hold. Recheck current owner authorization outside native database locks before committing proof changes. Reservation failure/outage must not refund opportunities or be confused with a bad PIN.

Expose native-only one-time consumption of accepted proof, bound to the exact original grant and original PIN generation, expiry and current enabled/hold/owner state. Consume atomically and record attribution/reference without PIN, JWT or raw provider payloads. A consumed/expired/revoked proof cannot become new authority through retries. Receipt loss means an uncertain result requiring reconciliation with the original journal, not another verification. Older retained proof rows lacking the new binding must not become consumable accidentally.

Test correct and refused grants, same-nonce altered binding, wrong targets/issuers/action, expiry, replays, rotation/revocation/holds, counter preservation and concurrent attempts. A test-only owner must be excluded from production packages and cannot establish real BPO acceptance.

## Privileged administration

Supply an explicit opt-in Keycloak profile and deployment instructions for named local administrators: password followed by a previously enrolled WebAuthn credential, with user verification required and no password/OTP/recovery-code fallback or SSO-cookie bypass. Guard the actual WebAuthn authenticator at both challenge and response boundaries, not only a preceding execution: a resumed authentication session or removed key must not fall through to registration. Always report configured-for to the flow engine, explicitly refuse absent two-factor WebAuthn credentials, and never enqueue a registration required action. The guard authenticates credentials; actual Admin REST permissions remain Keycloak's responsibility.

Prepare configuration offline and refuse ambiguous/unsupported changes. Do not silently modify master or existing clients. Disable direct password grants and unsafe interactive bypasses in the selected profile; validate client authentication-flow overrides and profile prerequisites explicitly. Keep account/bootstrap setup and transition separate so operators can enroll and verify permanent administrators before removing temporary bootstrap access. Never provide a universal emergency password or a general bypass client. Emergency access remains named, private, strongly authenticated, monitored and subject to institution-approved custody/dual-control/rehearsal.

Qualify with actual Keycloak and virtual FIDO2 authenticators in an isolated hosted realm: valid enrolled key plus password succeeds; missing key, password-only, wrong key and lack of user verification refuse. Test that no unintended enrollment or weaker alternate flow occurs. Document that virtual authenticators do not qualify the institution's physical hardware, attestation policy, recovery owners or network boundaries.
