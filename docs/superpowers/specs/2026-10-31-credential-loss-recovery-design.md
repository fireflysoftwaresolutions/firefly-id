# Credential-loss recovery through independent identity-proofing adapters

## Intent and authorization

The owner has approved advancing with the existing OpenPlatform KYC/KYB base and independent adapters to implement recovery when the previous password or authenticator is unavailable. This implements the boundary already documented in `docs/identity-proofing-evaluation.md`; it does not select an unapproved external vendor or change Jafly. Repository artifacts use American English. Product copy remains English/Spanish and retains the approved Firefly/Manrope light/dark design.

## Outcome

A customer can initiate recovery without their previous password, complete an independently verified identity-proofing case, and replace their local password and TOTP before an eligible authentication lock is removed. Old credentials and sessions cannot remain usable after activation. A proofing failure, unavailable dependency, administrative/fraud hold, changed identity link, stale generation/revision, replay or missing approved verifier refuses recovery. No ordinary token, impersonation or business permission is issued by recovery.

No real proofing provider/process has been approved. Shipping provider-neutral mechanisms and qualifying them using a test-classpath-only synthetic provider does not establish documentary/biometric assurance or enable production. Unconfigured adapters must deny. KYC/KYB CRUD status and the existing synthetic KYB adapters never authorize recovery.

## Ownership and isolation

- `core-common-kycb-mgmt` owns durable proofing cases, evidence references, one-time recovery authorizations, execution recording and database concurrency/audit.
- `domain-customer-kyc-kyb` owns customer proofing orchestration and independently replaceable provider adapters. It calls the actual Core producer through its genuinely generated SDK; generated sources are never hand edited. Domain owns no business/recovery database.
- Firefly Identity owns native local credential verification/replacement, its browser ceremony, current user/hold/link/generation/revision admission, factor enrollment and old-session retirement. It calls Domain over a distinct narrowly scoped authenticated channel. Credentials and enrollment secrets never leave Keycloak.
- Jafly is unchanged. Product receiving services use Spring Security and explicit per-action product policy. A workload identity is transport authority to request a case, not sufficient evidence to approve recovery.
- The existing Core/Domain SCA unlock protocol is unchanged. Credential-loss recovery has its own purpose and protocol; it cannot reuse a known-password attestation.
- Customers and employees remain separate issuers, configuration and authority. This customer KYC owner refuses STAFF. Native workforce recovery remains unavailable without an independently approved workforce owner; no customer case restores an employee or administrator.
- New implementation classes end in `Impl` and live in an `impl` subpackage. Preserve existing bean IDs/provider IDs. Do not merge, release, deploy or modify retained checkouts/databases. Existing authorization covers isolated candidate branches, hosted validation and draft PRs. All local JVM/database/container/dependency-download work is prohibited below the 12-GiB free-disk floor.

## Protocol and public behavior

Use separate native root `/firefly-recovery/lost-credentials`, separate Secure/HttpOnly/SameSite=Strict cookie and rotating CSRF, exact Origin and no-store. Add a discreet recovery entry only when this owner is configured. The existing known-password unlock remains distinct. No password reveal control, account-existence disclosure, remaining-attempt count or raw diagnostics.

1. Generic account-identification POST starts a bounded cookie-bound native ceremony without authenticating the claimant. Known, unknown, ambiguous and ineligible accounts receive the same public shape. Create an opaque decoy target binding where necessary. Starting a case is not admission to replacement. The provider journey must not distinguish account existence before independent identity evidence is verified.
2. Native sends an immutable server-generated binding to customer Domain. It includes exact issuer, realm, tenant, subject, existing party UUID, population, purpose `CREDENTIAL_REPLACEMENT`, lock generation, complete credential revision and unpredictable ceremony nonce. No email/name equality creates or links an account. Case preparation validates the native server ceremony independently; approval/consumption also require fresh current native eligibility. Unknown/decoy bindings can never pass final admission.
3. Domain starts the selected proofing provider session, retaining only opaque provider references in Core. The provider SPI is server-to-server: begin a session and verify an authenticated result. Browser redirects and user-supplied booleans are never proof. A selected adapter must authenticate callbacks, bind exact provider session/case/nonce/reference identity, enforce freshness, replay and all required checks. No generic public callback exists until an actual adapter owns its authentication contract. Initially the only successful adapter is in the test classpath, absent from production JARs and disabled without explicit fixture startup.
4. A verified result must positively bind the existing customer through an approved authoritative reference and establish required document/issuer authenticity, live matching capture, fraud checks and policy completion. Provider code/model/data licenses and actual thresholds are external acceptance requirements. Failed/unavailable checks do not become approval or a fabricated business rejection. Raw biometrics/documents remain with their evidence owner, never in Keycloak attributes or application JWTs.
5. Core records a bounded evidence reference and issues an opaque, short-lived authorization tied to the exact immutable binding, case, approved policy, evidence revision and a canonical execution UUID. There is no caller-supplied `approved` route. Grant issuance and consumption require authenticated Domain workload plus evidence verification and fresh native eligibility. Default case TTL 600 seconds; grant TTL at most 120 seconds and never beyond case expiry. No renewal on retries.
6. Native obtains and verifies authorization online, then presents new password/confirmation and new TOTP enrollment. Password satisfies the actual realm password policy/history and local password provider; new TOTP must be proven with a fresh valid code before consumption. Do not persist raw passwords. Any pending TOTP secret is protected in the native boundary using an explicitly provisioned 256-bit encryption key, not returned in URLs or logs. Browser and server limits bound all input. Unsupported credential types (including passkeys/foreign storage) refuse recovery until their retirement is explicitly implemented; do not silently leave an old authenticator usable.
7. Core atomically consumes the authorization once for its canonical execution. Native validates the consumed receipt online and performs the current-state check and mutation under the existing user/state database lock. Atomically replace password and TOTP, retire the superseded authenticators and support-PIN authority, clear only an eligible permanent-authentication lock, advance generation/revision and not-before, retire all online/offline sessions, enqueue a durable notification to the previously verified channel and write the native execution journal. Ordinary authentication remains disabled/purpose-restricted until all required factors are bound. No sequence of public reset-password/enable calls is allowed. Administratively disabled or held identities remain denied.
8. Domain/Core record the exact native execution through an independent authenticated journal check. Lost-response retry preserves original case, grant, execution, expiry and budgets; a committed native journal returns the same outcome without another mutation/consumption. No HTTP call runs while a native database lock is held. An expired unexecuted authorization cannot mutate; an expired executed journal permits audit reconciliation only, never another grant or enablement.
9. The customer receives a generic completion and signs in normally using the replacement factors. Notification delivery uses the approved native channel/outbox and is not replaced with a log statement. Preserve delivery state and retry evidence; SMTP/provider failure cannot silently disappear. Production activation remains disabled until actual notification delivery and bank procedure are accepted.

## Internal API contract

Core and Domain use `/api/v1/identity-recovery/cases`; JSON timestamps are UTC ISO-8601 and UUIDs canonical. DTOs are product-specific independent Java records in each owner, not shared Jafly types. Agree the exact producer DTOs before Domain/native implementations begin.

Required operations: create case (idempotent on binding/nonce), inspect case, confirm verified provider evidence (private adapter-owned call only), consume authorization, verify consumed authorization and record/verify execution. Provider result confirmation is not a public arbitrary approval endpoint: Core independently verifies evidence through its configured proofing port or signed provider/Domain evidence verifier and current native admission. Each operation has a separately authorized identity/action; wrong client, issuer, tenant, target, purpose or population is denied at each receiving boundary. Default-off Spring Security chains cover the entire path even if feature controllers are absent. Dedicated secrets come from environment/mounted files, never source. TLS redirects/trust-all are forbidden; requests and responses are bounded and time out.

The native private admission/journal contract is separate from public browser routes and scoped to explicitly configured grant-disabled KYC workload clients. It can attest only an existing server ceremony/current state or an exact committed execution. It cannot manufacture proofing evidence, reset credentials or enable a user. Domain and Core have distinct credentials and exact route/action permissions.

## Durable invariants

Case and grant state must be database-authoritative with row locks/CAS and unique constraints, not JVM maps. Use database time for expiry, immutable binding/evidence digests, preserved failure budgets and durable audit. Permit at most three rejected confirmations per ceremony/provider session. The subject/generation ledger counts at most three fully verified grant issuances, not unauthenticated claims or failed mandatory identity checks; duplicates/retries never create another opportunity. No UI count or silent counter reset. Add independently installer-owned SQL rather than automatically applying an unqualified retained-database migration. New isolated hosted databases may install it explicitly.

Native mutation and journal must share the native transaction. A lost response before native execution can leave a consumed grant pending for its same canonical execution only until original expiry. After commit the journal is the only mutation authority. Concurrent consumers/executors yield one grant consumption and one native mutation. Hold, link, credential or generation changes at any phase invalidate unexecuted work.
