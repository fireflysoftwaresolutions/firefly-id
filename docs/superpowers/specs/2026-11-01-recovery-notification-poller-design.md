# Recovery notification polling and supervision

The owner explicitly requested completing the existing Core-owned notification poller and its supervision. This implements that already selected operating boundary; it does not enable recovery in production or approve an SMTP/evidence provider. Jafly remains independent and unchanged. The owner selected KYC/KYB Core as the system of record, Domain adapters for a third-party verifier and eIDAS as the design baseline. No engine or vendor is selected; authenticated existing-party reference resolution and the approved assurance contract remain vendor-acceptance requirements.

## Owners and wire

Native Keycloak retains the durable notification outbox, encrypted prior destination, attempt budget, leases and send operation. Core KYCB owns a default-off scheduled poller and private aggregate supervision. Neither Domain nor a browser can dispatch or monitor notifications. No new database objects or public case/SDK operations are needed.

Native private RPC remains `/firefly-recovery/lost-credentials/rpc/{route}` under the exact configured issuer. Add route `notification-status`. `dispatch` accepts JSON `{ "limit": 1 }`, bounded to 1..10. Existing `{}` retains the manual limit of ten. Its response remains `{ "processed": n }`; processing is not a guarantee of delivery. The new poller always requests one row so a single call does not amplify SMTP latency. Strict bounded JSON and existing true TLS/body limits apply.

`notification-status` accepts `{}` and returns exactly: `observedAt` (UTC Instant), `pending`, `sending`, `retrying`, `delivered`, `failed`, `invalid`, `due`, `oldestDueDelaySeconds` (nonnegative integers). Counts use one realm-scoped database snapshot and database time. `retrying` counts pending rows with prior attempts; `due` includes pending rows and expired sending leases due now; invalid/null/unknown statuses are counted as invalid. No subject, email, case/execution ID, ciphertext, exception or provider content is returned. The operation never mutates or resets outbox state.

Configure the separate grant-disabled confidential client with realm attribute `firefly.reproofing.notification-workload-client-id`. It must differ from the Core and Domain ceremony clients. When configured, only that client may use `dispatch` and `notification-status`, and it cannot use prepare/admit/journal. Existing deployments without this attribute retain the previously qualified Core-only manual dispatcher; the new poller requires the dedicated client. All current grant-disable and fresh-client checks remain mandatory. No ordinary OAuth grant or financial permission is introduced.

## Core lifecycle and limits

Configuration prefix: `firefly.reproofing.notifications`. `enabled` defaults false and also requires `firefly.reproofing.enabled=true`. Required: `client-id`, `secret-file`, `monitor.client-id`, `monitor.secret-file`. Both identities and secrets are distinct from the case receiver/native ceremony caller. Outbound base URL is the existing exact issuer-native RPC URL, with trusted TLS and no redirects. Credential files are private, regular nonsymlink files; failures are generic and cannot log their contents.

Defaults: `poll-interval=PT30S`, `request-timeout=PT30S`, `stale-after=PT90S`, `overdue-after=PT2M`. Bounds: interval 1..300 seconds, request timeout 1..60 seconds, stale-after greater than interval+timeout and at most 3600 seconds, overdue-after 1..3600 seconds. The one-second lower interval is for isolated qualification; production examples use thirty seconds. Existing nonnotification HTTP clients retain their five-second timeout.

A product-owned managed Spring lifecycle schedules an immediate first cycle and fixed-delay cycles on its single scheduler thread. It permits at most one local reactive cycle in flight, bounds the whole dispatch/status sequence, cancels its future/subscription on shutdown, and releases the local gate after success, error or cancellation. Native leases fence multiple Core instances and ambiguous responses. An error cannot manufacture delivery, spend a recovery budget or launch another recovery. No scheduler or network call is created when disabled. No global Spring scheduling policy or Jafly behavior is changed.

Each cycle dispatches at most one eligible row then reads the aggregate status. Validate response counts, freshness, unknown fields and processed range before marking success. Counts must add without overflow, retrying cannot exceed pending, due cannot exceed pending+sending, and no-due implies zero due delay. Native observed time must be no more than 30 seconds ahead or 90 seconds behind Core's observation time; clock problems are unavailable, not fabricated healthy state. HTTP/TLS/auth/body/decoding/timeouts produce a bounded failure category, never raw exception text. A restart reobserves the same native durable queue; it never clears counters, leases or terminal failures.

## Supervision

Expose only authenticated HTTPS GET `/internal/identity-recovery/notifications` and its exact `/metrics` child in Core, using the separate monitor credential. Deny all other methods/subpaths and deny the whole path when disabled. Its conventional REST controller is hidden from the original producer OpenAPI. Existing case callers cannot read it; its credential cannot invoke case operations. Existing generic receiver policy remains composed independently.

Return a safe immutable process snapshot: state (`STARTING`, `HEALTHY`, `DEGRADED`, `UNAVAILABLE`, `STALE`), active-cycle flag, last attempt/success timestamps, consecutive failures and the last validated aggregate queue snapshot. Compute staleness when read, even if scheduling silently stops. A failed cycle is unavailable; missing initial success is starting; stale success is stale; failed/invalid/retrying rows or excessive due delay are degraded; otherwise healthy. Never present stale cached counts as a fresh successful observation.

Use existing Micrometer/Prometheus dependencies, prefix `firefly.reproofing.notifications`, fixed labels only. A private metrics wrapper owns its Prometheus registry; it must never be a `MeterRegistry` bean, global-composite member or global Actuator-discoverable registry. Inject only that private registry into the worker and close it with its lifecycle. Scrape only through the authenticated exact `/internal/identity-recovery/notifications/metrics` path. Neither an existing public global scrape nor an unrelated approved scraper may expose these private queue series accidentally. Global endpoint configuration/registries and application readiness remain unchanged.

Record cycle successes/failures, processed rows, consecutive failures, active cycle, last-success epoch, stale state and aggregate queue counts/due delay. No identity or dynamic exception/URL labels. Supply alert rules for absent/stale polling, transport failures, terminal failures/invalid rows and sustained retry/due backlog. The private status and metrics describe this worker independently.

Delivery remains at least once. The native eight-attempt budget, original lease tokens and failure evidence remain authoritative. Approved production SMTP must retain bounded connect/read/write timeouts (Keycloak 26.8.1 defaults each to 10,000 ms), trusted transport and monitoring ownership. No automatic failed-row replay/delete or email/contact replacement is supplied.

Preserve the current global feature-flag semantics: disabling reproofing stops its worker and closes its paths. Normal shutdown must quiesce new browser recovery ingress and drain/review pending notifications before disabling the runtime. Emergency disabling preserves the queue and requires operational follow-up; an externally configured absence alert must detect a missing expected worker. Do not change the global feature gate or fabricate successful empty-queue telemetry to conceal a disabled poller.

Include actual private monitoring positive/negative calls. Preserve old 48-control recovery and full 21-control loss recovery coverage at the new pins.

All JVM/DB/browser qualification runs remotely; no local JVM, DB, clones, heavy downloads or cleanup. Use existing isolated checkouts and retain source-parent/Jafly 26.10.23 fixtures. Named technical implementations end `Impl`; REST entry points, DTO/records/entities, authentic configuration/bootstrap, exceptions/CQRS and anonymous implementations retain their semantic roles. No generated Java edits, merge, release, production deployment, bank/provider acceptance or private handoff edits are authorized by this technical completion.
