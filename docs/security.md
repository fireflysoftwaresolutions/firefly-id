# Security model

Firefly Identity distributes a Keycloak identity surface. It is not the authoritative source for customer, workforce, institution, tenant membership, party records, or application authorization. Those boundaries must be approved against the actual platform contract before production provisioning is enabled.

## Trust boundaries

Keep customer, workforce, and institution populations in distinct realms with independent user stores, clients, roles, login policies, and federation/brokering configuration. Keep administrators in the administrative plane; do not make the public workforce or institution realm an administration realm. Production administrators require least privilege, phishing-resistant MFA, and access through a private administrative ingress. A realm is a logical identity boundary; deployments requiring stronger operational or legal isolation need separately operated instances/databases.

`sub` is the Keycloak identity reference. The examples `tenant_id`, `party_id`, and `staff_actor_id` are provisional server-managed references, not permission grants. The sandbox imports a declarative user profile component with unmanaged attributes disabled and those attributes editable/viewable only by administrators. Population-specific mappers emit `party_id` for customers/institutions and `staff_actor_id` for workforce, with UUID-shaped synthetic references. `tenant_id` is an opaque string. Hardcoded mappers emit `principal_kind=HUMAN` or `STAFF` and the actual example `client_id`; interactive backend clients are not machine principals. Only access tokens receive these attribute mappers; ID tokens and userinfo do not. Customers/institutions receive no staff identifier. Arbitrary account/profile fields and requested scopes cannot create an authoritative relationship.

For production, an authorized provisioning service must obtain these references from the authoritative platform, validate cross-tenant membership there, and write only approved fields using narrowly granted administration permissions. Do not grant end users manage-users, manage-clients, impersonation, role-mapping, or provisioning credentials. Do not map uncontrolled broker attributes, registration data, request headers, or frontend form values onto trusted claims. Changes to an email address do not change party or tenant identity. Runtime tests must attempt forged profile writes and broker/registration changes before accepting these controls. Backend authorization must independently validate the subject's current tenant relationship and relevant permission; token possession alone is insufficient.

## Protocol and secrets

Every population uses the selected permanent three-failure policy. A permanently disabled account has no timed release; password replacement must not re-enable it. Public failures and recovery acknowledgements remain generic and omit counters. The [recovery design](permanent-recovery.md) separates native blocking, approved recovery proof and full-platform access invalidation. Previously issued self-contained JWTs need receiver enforcement of current identity state; signature validation alone does not implement immediate blocking. Secure automatic unlocking and current-state receiver integration remain unqualified and production generation stays unavailable until their gates pass.

Use authorization code and PKCE S256 for browser and confidential interactive clients, exact callback and logout allowlists, and narrowly assigned audiences/scopes. Disable password/direct-access and implicit grants. Machine clients require their own reviewed client contract and credentials; the sandbox does not enable service accounts. The application validates signature, exact `iss`, intended `aud`, expiry, and approved algorithm. Reject tokens from another population's issuer even when a username or tenant value matches. Use state/nonce, short access-token lifetimes, protected refresh tokens, and session termination for logout and incident response.

No fixed password, API token, signing key, user credential, or private client secret is distributed. Sandbox generation creates random values locally under an owner-only parent directory, never logs them, and refuses overwrite. Mounted files are mode 0644 inside the owner-only state directory so the non-root Keycloak process can read local Compose secret mounts; local Compose cannot be relied upon to implement secret-file UID/GID remapping. `credentials.json`, Compose, and the ownership marker are mode 0600. Docker administrators and the owning host user can read these secrets. Use a real secret manager for production and restrict file ownership there.

The sandbox entrypoint reads mounted files and exports `KCRAW_DB_PASSWORD` and `KCRAW_BOOTSTRAP_ADMIN_PASSWORD`. This uses the [literal environment configuration source supported by pinned Keycloak 26.8.1](https://github.com/keycloak/keycloak/blob/26.8.1/docs/guides/server/configuration.adoc). Generic Keycloak `*_FILE` support is not assumed. PostgreSQL's image supports `POSTGRES_PASSWORD_FILE`; the initialization script creates a dedicated nonsuperuser application login/database. The bootstrap database superuser secret is not mounted into Keycloak. Changing an initialization secret does not rotate a password on retained PostgreSQL data.

Use production TLS for browser, backchannel, proxy-to-Keycloak, and database connections. Keep keys out of image layers and build arguments. Provision a narrowly controlled temporary bootstrap administrator through a supported bootstrap operation, establish permanent least-privileged administration, then remove temporary accounts and bootstrap secret injection. Review signing-key rotation, emergency revocation, session invalidation, and client-secret rotation against real consumers.

## Exposure and audit

The sandbox's HTTP, SMTP without authentication/TLS, synthetic claims, and shared local bootstrap account exist only on the isolated local example. They must not be promoted to production. Mailpit is a local sink, never a production SMTP provider or external relay.

A separate administrative hostname does **not** block the Admin REST API on the public hostname. The ingress must restrict `/admin/` and the administrative realm paths; permit only necessary public realm/protocol/account/resources endpoints. Never proxy management port 9000 publicly. Use TLS re-encryption, overwrite forwarded headers at the ingress, configure exact trusted proxy addresses, and firewall direct service access. [Keycloak's pinned reverse proxy guidance](https://github.com/keycloak/keycloak/blob/26.8.1/docs/guides/server/reverseproxy.adoc) documents these requirements.

Collect identity/admin audit events with retention limits and restricted access. Do not record tokens, credentials, full personal profiles, email bodies, or authorization codes. The sandbox enables events with seven-day expiry and disables admin event representation details; production forwarding, tamper resistance, alerting, data residency, retention, deletion, and incident response remain deployment decisions. Themes must preserve built-in CSRF/action tokens and authenticator semantics; security controls belong to the server, not CSS or browser-only checks.

Report vulnerabilities privately to the repository maintainers through the organization's established security channel. No specific external mailbox or service is defined by this repository.
